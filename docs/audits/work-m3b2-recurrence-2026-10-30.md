## Scope and architecture

M3-B2 completes the **first context-aware recurring-rule binding flow** inside the M3-B1 Service Engagement list, without changing the Work Items router, canonical renderer, scheduler, service billing, Time CAS or native WordPress authorizations.

A new **Execution status** action on an Engagement opens the existing Base Modal. It lazily reads a specific calendar month's authoritative execution status via `PublicApi\ServiceOperations::period()` → `ServiceOperations\Periods::resolve()`. This preserves exact `not_scheduled`, `attention`, `overdue`, `blocked`, `planned`, `in_progress`, `not_delivered` and `completed` meaning; the client receives translation labels from the **existing** `Admin\ServiceOperations::statuses()` and does not infer statuses from rule existence.

The dialog searches **active, untrashed RecurrenceRules** with canonical `Repository\RecurrenceRules::search_page()`, bounded at 25 candidate rows per source page. The server filters rules on **exact Project, Service, Internal/Customer context and customer provider/type/id**, excludes already linked IDs, and returns only rule ID, title, frequency and next date. It does not disclose customer identity. Because this filters a bounded canonical source page, intermediate pages can legitimately have zero eligible records while later pages remain. The client preserves source pagination and does not treat those pages as an overall no-results state.

Binding requires a selected valid rule and explicit `effective_from` date (client defaults to the Engagement's start). Server rechecks actor permissions inside both GET/POST callbacks, validates direct callback types/date, verifies active/eligible matching rule again, then calls **only** the existing `PublicApi\ServiceOperationsActions::bind_rule()`. That action owns the canonical audited transaction, duplicate checks, effective-date and context validation. No new scheduler or ledger writer; no new Work Item is generated by this UI action. HTTP error or invalid response leaves modal open with an error, never falsely reports success.

Backend: `Transport\Rest\WorkspaceEngagementRulesController`, nested GET/POST-only Work endpoint `/workspace/engagements/{engagement_id}/rules`. Reuses `WorkspaceEngagementsController::can_manage`; no widening of UWE-03B1 route regex or Time-only access. Body is small and no customer data is surfaced.

Frontend: `assets/js/workspace/engagement-rules.js` imported by M3-B1 `engagements.js`. No secondary Base Modal implementation. Handles search, month changes, bounded source pagination, abort/cancellation, role-403/invalid status, single-dialog state, and refreshes Engagements on success. The authoritative native Service Operations and Recurring Work routes remain available from Work for creating new rules, coverage, invoicing and other not-yet-migrated workflows.

Deployment: the new module is included in the same deterministic, recursive content-hashed ZIP ESM graph and checked by `src/Admin/Assets.php` before enqueue. Its REST URL is rendered by WordPress with an `__id__` placeholder and safely replaced by client, supporting both pretty permalink and query-style `rest_url()` deployments. Only existing translated strings are used. CSS remains scoped to Work/Modal UI.
